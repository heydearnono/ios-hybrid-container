# 工程事实

- **更新时间**：2026-09-22
- **适用版本**：Xcode 26.0 以上（26.2 与 27.0 两台机器上都实测构建通过）/ Swift 随 Xcode 走
- **采集方式**：两台机器命令行实测（见「环境基线」）；另有一台 Xcode 16.3 的机器提供过真实报错样本

这份文档是**端侧工程事实**：工具链怎么咬合、构建会在哪里陷住、环境怎么自检。它在重建时从旧仓
（tag `pre-rebuild`）那份踩坑清单里分流出来，只留下对这个容器仍然成立的部分。

平台事实（平台声明、还成立的技术约束）反过来，归 `pro` 的里程碑文件，不在这里。

第一次跑这个仓卡住，原因**几乎都不是代码问题**，而是三件事：仓库不含 `.xcodeproj`、
工程要求 Xcode 26.0 以上、iOS 模拟器运行时要单独下载。

## 先跑这段自检

```bash
sw_vers -productVersion                   # 需 >= 15.6（Xcode 26.2 的最低系统要求）
uname -m                                  # arm64 / x86_64，决定下哪个 Xcode 安装包
xcodebuild -version                       # 需 Xcode 26.0 以上（27.0 已实测通过）
xcodegen --version                        # 需 2.46.0 以上
xcrun simctl list runtimes | grep -i ios   # 必须有 iOS 26.0 以上的运行时
```

五项都满足，直接 `./scripts/verify.sh`，退出码 0 就算通了。缺哪一项，对应下面同名小节。

## 1. 用 Xcode 打开文件夹失败

**症状**：clone 之后 `open .` 或在 Xcode 里选这个目录，报
`Failed to open a document for ...，but no underlying error was returned`。文案没说清缺什么。

**原因**：`.xcodeproj` 是 xcodegen 的生成物，按约定不入库（见 `.gitignore`）。Xcode 在目录里找不到
`.xcodeproj` / `.xcworkspace` / 根级 `Package.swift`，就吐这句。

**修法**：在**仓库根目录**（`project.yml` 所在那层）生成工程。

```bash
brew install xcodegen        # 没装过才要
xcodegen generate            # 产出 Crab.xcodeproj
open Crab.xcodeproj
```

`xcodegen generate` 默认读**当前目录**下的 `project.yml`，输出目录取 spec 所在目录，所以必须在根目录
跑。从别处跑要显式指定 `--spec /path/to/project.yml`。`./scripts/verify.sh` 不受此限制 —— 它自己算出
仓库根并 `cd` 过去，且第一步就是 `xcodegen generate`。

**自证**：`ls Crab.xcodeproj` 存在。

## 2. 没有可用的运行目标

**症状**：点运行报 `No supported iOS devices are available.`，伴随
`A build only device cannot be used to run this target.`

**原因**：Xcode 为这个 scheme 算出的合格目标是**空的**，只剩 `Any iOS Device` 这个 build-only 占位项。
三种成因，可能同时成立：

**(a) Xcode 太老。** 工程的 deployment target 是 iOS 26.0（`project.yml` 的
`options.deploymentTarget.iOS`，取值由 `pro` 的 M1 定），Xcode 会把低于它的模拟器全部过滤掉。
Xcode 16.x 带的是 iOS 18.x SDK 与运行时（18.x < 26.0，全部不合格），所以那台机器上装再多模拟器也一个
都不合格。老 Xcode 也**用不了**新下载的 iOS 26.2 运行时 —— 运行时要有对应 Xcode 的 SDK 支持才会被列进
目标。新 Xcode 上同理：装了 iOS 18.6 运行时，那批模拟器仍会被判为 ineligible，原文
`18.6 doesn't match Crab.app's iOS Simulator 26.0 deployment target` —— 那是过滤器在正常工作，
**不是故障，也不得为此下调 26.0**（那个值由 `pro` 的 M1 定）。

顺带一个只在装了多个运行时的机器上才咬人的点：`-destination` 里**只写机型名不写 OS 时，
xcodebuild 按「最新已安装运行时」解析**，于是机型只存在于旧运行时就会报

```
Unable to find a device matching the provided destination specifier:
        { platform:iOS Simulator, OS:latest, name:iPhone 17 Pro }
```

机型在、运行时也在，只是这个组合不存在。`scripts/` 下的脚本因此不按名字用设备：
`scripts/lib/sim-device.sh` 先解析出一台可用模拟器的 UDID，`xcodebuild` 与 `simctl` 一律按
`id=<UDID>` 用。手敲 `xcodebuild` 撞上这句，补一段 `,OS=<版本>` 或改用 `id=` 即可。

**(b) 没装 iOS 运行时。** 升级完 Xcode 后最容易再撞一次的坑，报错一模一样，看起来像「升级没生效」。
**iOS 模拟器运行时不随 Xcode 打包**，是单独下载的组件 —— 本机 `xcrun simctl runtime list` 显示它是一个
独立的 Disk Image（7.8 G 压缩、挂载后 16 G），放在 `/Library/Developer/CoreSimulator/`，不在
`Xcode.app` 里面。装完 Xcode 要进 **Xcode → Settings（Cmd+,）→ Components** 下载
**iOS 26.0 以上的 Simulator 运行时**。

**(c) 目标停在了一台离线真机上。** Xcode 记住上次选的设备，设备一断开就退化成 build-only 目标。
修法：工具栏 scheme 名右边的目标下拉 → iOS Simulators 分组里选一台，例如 `iPhone 17 Pro`。

**自证**：这条命令打印的就是 Xcode 认可的目标列表，不用开 Xcode 猜。

```bash
xcodebuild -project Crab.xcodeproj -scheme Crab -showdestinations
```

只吐出 `Any iOS Device` 占位项、后面跟着一片 `Ineligible destinations`，就是上面三种成因之一。

## 3. 选错成 My Mac

**症状**：目标选 `My Mac (Designed for iPad)`，报
`Xcode doesn't support My Mac's macOS 15.7.3 (24G419)`（本机 `-showdestinations` 实测到这条
`Ineligible destinations`）。

**原因**：「Designed for iPad」要求宿主 macOS 能支撑对应 iOS SDK 的运行环境，macOS 15.x 撑不起
iOS 26 的兼容运行。**这个目标在本项目里没用**，选 iOS 模拟器就行，不必尝试修它。

## 4. Swift tools 版本不匹配

**症状**：`package '<名字>' is using Swift tools version 6.2.0 but the installed version is 6.1.0`

**现在还撞不上**：本仓暂时没有 `Package.swift`（M1 只有一个原生壳子）。**M2 起逻辑落进
`Packages/` 之后**，包清单会声明工具链版本，老 Xcode 就会报这句。它和第 2 节是同一个根因、两个独立的
失败点：这条是「代码根本编不了」，第 2 节是「选不了设备」。修法都是升级到 Xcode 26.0 以上，
**不需要升 macOS 26**，见下面第 6 节。

## 5. 真机跑不起来

**原因**：签名是**刻意关掉的**，在 `project.yml` 的 `settings.base` 里：

```yaml
CODE_SIGNING_ALLOWED: NO
CODE_SIGNING_REQUIRED: NO
CODE_SIGN_IDENTITY: ""
```

真机路径会拉起签名交互，一有人工对话框，AI 与 CI 的闭环就断了。而五个里程碑一律在模拟器上验收，
`pro` 的 M1 已经写明本阶段走 Simulator 不校验签名。

**所以真机不是「配一下就能跑」，而是当前不支持的路径。** 真要上真机：恢复签名设置、配好
Development Team、设备系统 ≥ iOS 26.0，并且明白这条路上的验证不再是无人工的。

## 6. 要不要升到 macOS 26

**构建这个工程：不需要。** Xcode 26.2 自身的 `LSMinimumSystemVersion` 是 **15.6**
（读 `/Applications/Xcode.app/Contents/Info.plist` 得到），本机就是 macOS 15.7.3 + Xcode 26.2，
`verify.sh` 全绿。只要宿主 ≥ 15.6，装 Xcode 26.0 以上就够。

## 7. 磁盘空间

安装前留够空间，本机实测占用：

| 项目 | 体积 |
| --- | --- |
| `Xcode.app`（解压后） | 4.7 GB |
| iOS 26.2 运行时（挂载后） | 16 GB |
| iOS 26.2 运行时磁盘映像（压缩态） | 7.8 GB |

加上 `.xip` 本身和解压中间态，**建议预留 30 GB 以上**（这个数字是估算，不是实测）。空间不足时
`.xip` 解压会在末尾失败，且不会明确告诉你是空间问题。

## 8. 下哪个 Xcode 安装包，装了多个怎么办

Apple 下载页给两个包：`uname -m` 输出 `arm64` 就下 Apple silicon 版（体积更小，功能无差异）；
输出 `x86_64` 是 Intel 机器，必须下 Universal 版。

装多个 Xcode 时命令行默认指向哪个由 `xcode-select` 决定，改完记得核对：

```bash
sudo xcode-select -s /Applications/Xcode.app
xcodebuild -version        # 应输出你打算用的那个版本（26.0 以上）
```

## 9. 报错像是「修了也不消失」

Xcode 的 Issue navigator 会留着上一次构建的问题，升级 Xcode 后不重新构建，旧报错还挂在那里。
⚠️ 未验证（未在本机复现，属合理推断）：Cmd+Shift+K 清理 → File → Packages → Reset Package Caches →
重新构建，应该就清掉了。

判断是不是残留有个可靠办法：**命令行不读 Xcode 的 UI 状态**，`./scripts/verify.sh app` 通过就说明当前
工具链没问题。

顺带一个诊断经验：**先确认报错来自哪台机器。** 本机只有一个 `/Applications/Xcode.app`（26.2）、
两处 `Toolchains` 目录都不存在、`TOOLCHAINS` 未设置 —— 这种配置下不可能报出旧版本号。出现旧版本号，
就是另一台机器或旧报错残留。

## 10. 重建残留：git 看不见的空壳目录

**症状**（两种，成因同一个）：

- `./scripts/verify.sh logic` 报 `Could not find Package.swift in this directory or any of its
  parent directories.` —— 看起来像 SwiftPM 坏了
- 目录里冒出一个跟当前工程名对不上的 `AILab.xcodeproj/`，而 `git status` 是干净的

**原因**：重建那一笔（`44ac60c`）把源码从**仓库**里删了，磁盘上剩下的全是 `.gitignore` 忽略的
东西，git 因此一个都不报。实际清掉过三个：

| 残留 | 里头剩什么 |
| --- | --- |
| `AILab.xcodeproj/` | 旧 `project.yml`（那时工程叫 AILab）的生成物 |
| `Packages/AICore/` | 只剩一个空的 `.swiftpm/` |
| `Packages/AIFeatures/` | 只剩一个空的 `.swiftpm/` |

目录还在、内容是空的，于是按「目录存在」去判的脚本就踩空 —— `verify.sh` 的 `run_logic` 现在改判
`Package.swift` 在不在，不再判目录，这条报错不会再由它引出来。

**修法**：先 `-n` 看清单，看准了再删，别一上来就 `-f`。

```bash
git clean -xdn                               # n = dry run，只打印会删什么
git clean -xdf -- Packages AILab.xcodeproj   # 看准了再删，路径限定住
```

⚠️ **`-x` 会把被 `.gitignore` 忽略的也算进去**，清单里会混着 `.env` / `.env.*` / `*.p8` /
`Secrets.swift` / `Secrets.xcconfig` 这类本地密钥与配置（本仓 `.gitignore` 明确忽略它们）。
**别一把全删**，按路径挑着删，或先把要留的挪开。

## 门槛表：每条约束写在哪

改这些数字之前先知道它由谁决定，否则会漏改。**前三项的取值来自 `pro` 的取值表，本仓不自定。**

| 约束 | 值 | 写在哪 | 谁定的 |
| --- | --- | --- | --- |
| App 运行时下限 | iOS 26.0 | `project.yml` · `options.deploymentTarget.iOS` | `pro` M1 |
| 标识 | `net.xiaoluzhu.crab` | `project.yml` · `PRODUCT_BUNDLE_IDENTIFIER` | `pro` 取值表 |
| 应用版本 | `0.1.0` | `project.yml` · `MARKETING_VERSION` | `pro` 取值表（UA 拼成 `Crab/0.1.0`） |
| 中文显示名 | 螃蟹 | `App/Resources/zh-Hans.lproj/InfoPlist.strings` | `pro` M1 |
| Swift 语言模式 | 6.0 严格并发 | `project.yml` · `SWIFT_VERSION` / `SWIFT_STRICT_CONCURRENCY` | 本仓 |
| xcodegen 下限 | 2.46.0 | `project.yml` · `minimumXcodeGenVersion` | 本仓 |
| 签名 | 全部关闭 | `project.yml` · `CODE_SIGNING_*` | 本仓 |
| 构建工具链下限 | Xcode 26.0 以上（27.0 实测通过） | 本文件「先跑这段自检」那段 | 本仓（deployment target 26.0 决定的下限） |

`verify.sh` 会把前四项从**构建产物**里读出来和取值表比一遍，改漏了当场报错，不靠走查。

## 这些是设计使然，不要「修」

| 现象 | 为什么 |
| --- | --- |
| 仓库没有 `.xcodeproj` | 生成物不入库，工程结构改 `project.yml`；避免去动几千行带 UUID 的 pbxproj |
| 签名全关 | 保证验证链条无人工交互 |
| 中文名要一份 `.lproj` 资源 | 只在 Info.plist 里写 `CFBundleDisplayName` 落不到中文名 |
| `scripts/probe.sh` 现在退出码非零 | 探针页还没接（M2 起）。它刻意不打印假的 `PASS`，也不打印会被误读成真失败的 `FAIL` |
| M1 阶段没有 `Packages/` | 那时还没有可在宿主 macOS 上跑的逻辑，`verify.sh logic` 会明说这一档是空的 |
| 不同机器上 `verify.sh` 挑到的模拟器不一样 | 机型写死会在「机型只存在于旧运行时」的机器上挑不出设备（第 2 节 (a)）。挑到哪台不影响判据，那行选中结果会打出来留痕 |

## 环境基线

两台机器上都实测过，**两台并列摆着比替换掉更有用** —— 它们正好证明这个工程跨 Xcode 两个大版本
都构建得起来。**跑一条命令即可复核的事实写下来只会过期**，所以这里只记采集当时的样子，
出问题时以上面那五条自检命令的输出为准。

| 项目 | A：2026-09-17 实测 | B：2026-09-22 实测 |
| --- | --- | --- |
| macOS | 15.7.3（Darwin 24.6.0），Apple Silicon | 未记 |
| Xcode | 26.2（Build 17C52） | **27.0（Build 27A266a）** |
| Swift | 6.2.3 | 随 Xcode 27.0 |
| xcodegen | 2.46.0 | 2.46.0 |
| 模拟器运行时 | **iOS 26.2（23C54），仅此一个** | **三个并存：18.6 / 26.3.1 / 27.0** |
| 可用 iPhone | 17 Pro / 17 Pro Max / 17 / 16e / Air | 27.0 上：17、17e、18 Pro、18 Pro Max、Air<br>26.3.1 上：16e、17、17 Pro、17 Pro Max、17e、Air |

A 上还有 iPad Pro 13-inch (M5) 等 iPad 机型。B 那台上的 iOS 18.6 模拟器会被 deployment target
过滤掉（见第 2 节 (a)），能用的是 26.3.1 与 27.0 这两批。

**机型不写死。** 脚本自己挑设备：不设 `CRAB_SIM_DEVICE` 就在全部可用 iPhone 里取运行时最高的那台，
设了就在同名设备里取运行时最高的那台，之后一律按 UDID 用（`scripts/lib/sim-device.sh`）。
代价是不同机器可能挑到不同设备，所以那行「模拟器：机型 · 运行时 · UDID」要留在运行记录里 ——
M1–M4 没有一条判据依赖屏幕尺寸，挑到哪台不影响结论，但得看得见这一跑用的是哪台。

A 那台**只有一个运行时**，做不了跨版本行为对比（比如 iOS 26.0 与 26.2 的差异）；B 那台三个并存，
需要对比时用它，或通过 Xcode → Settings → Components 下载历史运行时。

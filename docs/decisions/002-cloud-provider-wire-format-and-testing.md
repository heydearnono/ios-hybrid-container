# 002 · 云端提供方的线格式、流式语义与测试策略

- **日期**：2026-09-03
- **状态**：已采纳
- **相关调研**：[`../03-cloud-llm/streaming-in-swift.md`](../03-cloud-llm/streaming-in-swift.md)、
  [`001-ios-foundation-and-model-abstraction.md`](001-ios-foundation-and-model-abstraction.md)

## 背景

ADR 001 定了「云端为主线、端侧做增强」，但没定云端那条线具体长什么样。
真要写实现，有三个绕不开的决定，而且都受同一个硬约束逼迫：

**后端代理还不存在，厂商凭证也还没有。** 也就是说，实现必须在「无法访问任何真实端点」
的前提下写完并且被验证 —— 否则整个云端主线就得停在等后端，而后端属于用户决策（backlog 03 P0）。

叠加项目的总约束：每一步都必须能被机器无人工干预地验证。

## 考虑过的选项

**（一）线格式**

1. **OpenAI 兼容的 `/v1/chat/completions`** — 事实标准，绝大多数厂商与开源代理都兼容。**采纳**。
2. 抽象出中立的自有格式 + 各厂商适配层 — 更干净，但在只有零个真实端点的情况下，
   这个抽象是凭想象设计的，几乎必然要在接第一个真端点时重写。放弃。
3. 绑定单一厂商的原生 SDK — 换厂商即重写，且把厂商 SDK 的并发模型带进核心层。放弃。

**（二）流式语义方向**

1. **统一到累积快照（cumulative snapshot）**，云端 delta 在提供方内部累加。**采纳**。
2. 统一到增量（delta），端侧快照在提供方内部做差分。放弃 —— 见理由。

**（三）测试策略**

1. **在测试里起一个只绑回环的真 HTTP/1.1 服务器**（`NWListener`）。**采纳**。
2. 自定义 `URLProtocol` 打桩 — 更快，但绕过整个网络栈。放弃 —— 见理由。
3. 只做单元测试，等真端点再做集成测试 — 等于把最容易出错的部分无限期挂账。放弃。

## 决策

云端提供方按 **OpenAI 兼容线格式**实现；流式在抽象层**只暴露累积快照**，
delta→快照的转换是提供方的内部实现细节；集成测试打**本地起的真 HTTP 服务器**，
不打桩 `URLProtocol`。

## 理由

- **快照方向不可逆**。Apple Foundation Models 的流式输出是累积快照而非 delta
  （WWDC25 286 原话「Instead of raw deltas, we stream snapshots」，
  见 [`../01-on-device-llm/foundation-models-overview.md`](../01-on-device-llm/foundation-models-overview.md)）。
  从 delta 累加成快照是无损的；反过来对快照做差分，则要求「后一片一定以前一片为前缀」这条
  额外假设成立。⚠️ 未验证：Apple 没有承诺快照只会追加不会修订，而结构化输出的
  partially-generated 类型天然会让先前字段被填补或改写。
  在没有这个承诺的前提下，只有「统一到快照」这个方向两边都成立。
  连带好处：UI 直接赋值，不需要 append，也就不存在「漏了一片就永久错位」这类 bug。
- **真服务器比 `URLProtocol` 多测到的东西，恰好是最容易出错的部分**：UTF-8 多字节字符被
  TCP 分片切断、服务端不发 `[DONE]` 就关连接、连上了但一直不吐字节。
  这三条现在都有测试，而它们在 `URLProtocol` 方案下全都测不到。
  代价（约 0.4s 的测试耗时）远小于收益。
- **回环监听不触发 macOS 防火墙弹窗**（写之前用独立小程序验过）。这点是必要条件：
  弹窗需要人点，会直接破坏「机器无人工干预地验证」。
- **OpenAI 兼容格式让「后端就位」变成配置改动而不是代码改动**。当前状态已经做到：
  真实装配走 `ProviderFactory.makeRouter(cloudBaseURL:model:credential:)`，
  UI 一行不用改。

顺带定下两条与安全直接相关的形态，理由已在 ADR 001 与 03 主线的安全底线里说过，这里只记结果：

- 凭证入口是 `@Sendable () async throws -> String?` **闭包**，配置类型不接受字符串常量 ——
  从类型上堵掉「把 API Key 写成常量」这条路。
- `availability()` **不发探测请求**，只看有没有凭证。探测要花一次往返和一次计费，
  而且此刻可用不保证下一秒可用 —— 竞态消不掉，只能靠请求自身的错误处理兜住。

## 代价与风险

- 🔴 **线格式仍未被真实端点验证过**。stub 服务器是我自己写的，它只能证明
  「解析器和我的假设一致」，证明不了「我的假设和厂商一致」。
  首次接真端点时，`usage`、`tool_calls`、错误载荷的实际形状都可能对不上。
  已在笔记里标 ⚠️ 未验证。
- 🔴 **绑定 OpenAI 兼容格式，意味着接不兼容的厂商时需要写适配层**。
  接受这个代价：适配层等有了真实需求再写，比现在凭空设计中立格式更可能对。
- 🟡 **测试要起真 socket**，比纯内存测试慢，且理论上受运行环境网络策略影响
  （CI 容器若禁回环监听会失败）。目前无 CI，风险未暴露。
- 🟡 **刻意偏离 SSE 规范一处**：流结束时不完整的事件规范要求丢弃，本实现补一次派发。
  代价是遇到真正被截断的响应时，会把半个事件当成完整的交出去。
  权衡结论是「丢最后一个 token」比「偶尔多交一个不完整事件」更糟。
- 🟡 **断线重连未做**，流中途断开表现为抛错。已作为独立条目留在 backlog 03 P1。

## 什么情况下应该重新评估

- 后端代理选定的厂商**不兼容** OpenAI 的 chat-completions 格式 → 重新评估选项（一）。
- 出现「需要在流式过程中把 token 逐个交给下游」的场景（例如逐 token 播放 TTS）→
  快照语义会逼着下游自己做差分，此时重新评估选项（二）。
- 引入 CI 且环境禁止回环监听 → 重新评估选项（三），但方向应是换 CI 环境而不是退回打桩。
